## 三、实验整体逻辑分析

### 3.1 本章节的逻辑主线

本章围绕“如何让一个最小操作系统内核被启动并运行起来”展开。相比完整操作系统，lab1 只保留了最基本的骨架：内核镜像能够被 QEMU/OpenSBI 加载到指定内存地址，CPU 能够跳到内核入口执行代码，内核能够完成最基础的 C 运行环境准备，并通过 OpenSBI 输出一行启动信息。

本章的整体启动链路可以概括为：

```text
QEMU 复位启动
  -> 从 0x1000 执行复位代码
  -> 进入 OpenSBI 固件
  -> OpenSBI 完成基础初始化
  -> QEMU loader 将内核镜像放到 0x80200000
  -> CPU 跳转到 0x80200000
  -> 执行 kern_entry
  -> 设置内核栈 sp
  -> 跳转到 kern_init
  -> 清空 .bss 段
  -> 调用 cprintf 输出启动信息
  -> 进入死循环
```

### 3.2 功能的逐步实现

1. 首先确定内核加载地址和入口点。

   `tools/kernel.ld` 将内核基地址设置为 `0x80200000`，并指定入口符号为 `kern_entry`。这样 OpenSBI/QEMU 将控制权交给内核时，CPU 能够从正确的位置开始执行。

2. 接着准备汇编入口和内核栈。

   `kern/init/entry.S` 中的 `kern_entry` 是内核第一段执行的代码。它先把 `sp` 设置为 `bootstacktop`，为后续 C 函数调用准备栈空间，然后跳转到 `kern_init`。

3. 然后进入 C 语言内核初始化。

   `kern/init/init.c` 中的 `kern_init` 清空 `.bss` 段，保证未初始化的全局变量符合 C 语言语义，然后调用 `cprintf` 输出启动信息。

4. 最后通过 OpenSBI 完成控制台输出。

   内核不能直接使用 Linux 的 `printf` 或 glibc，因此 lab1 自己提供 `cprintf`、`printfmt`、`console` 和 `sbi_call`。输出链路为：

```text
cprintf
  -> vprintfmt
  -> cputch
  -> cons_putc
  -> sbi_console_putchar
  -> sbi_call
  -> ecall
  -> OpenSBI 输出字符
```

### 练习 1：理解内核启动中的程序入口操作

阅读 `kern/init/entry.S` 内容代码，结合操作系统内核启动流程，说明指令 `la sp, bootstacktop` 完成了什么操作，目的是什么？`tail kern_init` 完成了什么操作，目的是什么？

#### 回答

在 `kern/init/entry.S` 中，`kern_entry` 是内核开始执行后的第一个入口点。OpenSBI 将内核镜像加载到 `0x80200000` 后，会把 CPU 的控制权交给这里。此时内核还没有完成 C 语言运行环境的初始化，尤其是还没有可用的栈，因此需要先手动设置栈指针。

```asm
la sp, bootstacktop
```

这条指令的作用是把符号 `bootstacktop` 的地址加载到 `sp` 寄存器中。`sp` 是 RISC-V 中的栈指针寄存器，用来指向当前栈顶。

在 `entry.S` 后面定义了：

```asm
bootstack:
    .space KSTACKSIZE
bootstacktop:
```

这里预留了一段大小为 `KSTACKSIZE` 的内核栈空间，`bootstack` 表示栈底，`bootstacktop` 表示栈顶。由于 RISC-V 的栈通常从高地址向低地址增长，所以初始化时要把 `sp` 设置为 `bootstacktop`。

这样做的目的是为后续执行 C 函数准备栈空间。C 函数调用过程中可能需要保存返回地址、保存寄存器、传递参数、存放局部变量等，这些都依赖栈。如果不先设置 `sp`，后面直接进入 `kern_init`，函数调用和局部变量访问就可能使用无效地址，导致内核运行错误。

```asm
tail kern_init
```

这条指令的作用是跳转到 C 语言函数 `kern_init`，也就是进入真正的内核初始化逻辑。`kern_init` 中会清空 `.bss` 段，然后通过 `cprintf` 输出启动信息，最后进入死循环。

`tail` 是一种尾调用跳转。它会直接跳到 `kern_init`，而不是像普通函数调用那样保存返回地址后再调用。这里使用 `tail` 是合理的，因为 `kern_entry` 只是启动入口，不需要在 `kern_init` 执行完后再返回；而且 `kern_init` 被声明为 `noreturn`，最终会进入无限循环。因此，`tail kern_init` 的目的就是把控制权从汇编入口永久交给 C 语言内核入口。

总结来说，`la sp, bootstacktop` 完成内核栈初始化，为 C 语言运行环境做准备；`tail kern_init` 完成从汇编启动阶段到 C 语言内核初始化阶段的跳转。这两条指令共同完成了内核启动早期最关键的交接工作。

### 练习 2：使用 GDB 验证启动流程

为了熟悉使用 QEMU 和 GDB 的调试方法，本练习使用 GDB 跟踪 QEMU 模拟的 RISC-V 从加电开始，直到执行内核第一条指令，即跳转到 `0x80200000` 的整个过程。

#### 调试过程

首先在一个终端启动 QEMU 调试模式：

```bash
make debug
```

该命令会启动 QEMU，并带上 `-s -S` 参数。其中 `-S` 表示 CPU 启动后立即暂停，`-s` 表示 QEMU 在本机 `1234` 端口等待 GDB 连接。

然后在另一个终端中启动 GDB：

```bash
make gdb
```

连接成功后，先查看当前 PC：

```gdb
info registers pc
x/10i $pc
```

可以观察到，RISC-V 虚拟机加电后的第一条指令位于地址 `0x1000` 附近。这个地址不是我们内核的地址，而是 QEMU 模拟的复位入口，也就是虚拟机器加电后首先执行的固件/启动代码区域。它的主要作用是完成最早期的启动跳转，进入 OpenSBI 所在的固件代码。

接着在内核入口地址设置断点：

```gdb
b *0x80200000
c
```

继续执行后，GDB 会在 `0x80200000` 停下。根据当前编译生成的符号表，`0x80200000` 正好对应内核入口函数 `kern_entry`：

```text
0000000080200000 kern_entry
000000008020000a kern_init
0000000080201000 bootstack
0000000080203000 bootstacktop
```

在 `0x80200000` 处反汇编可以看到：

```asm
0x80200000 <kern_entry>:    auipc sp,0x3
0x80200004 <kern_entry+4>:  mv    sp,sp
0x80200008 <kern_entry+8>:  j     0x8020000a <kern_init>
```

这几条指令对应源代码中的：

```asm
la sp, bootstacktop
tail kern_init
```

也就是说，内核第一条指令开始执行后，首先把 `sp` 设置为 `bootstacktop`，即 `0x80203000`，为 C 语言函数运行准备内核栈。随后跳转到 `kern_init`，进入 C 语言编写的内核初始化逻辑。

可以继续单步执行：

```gdb
si
info registers pc sp
si
info registers pc sp
si
info registers pc sp
```

观察结果表明，执行 `la sp, bootstacktop` 后，`sp` 被设置到内核栈顶附近，即 `0x80203000`。继续执行后，控制流跳转到 `0x8020000a`，也就是 `kern_init`。

进入 `kern_init` 后，反汇编显示它会执行以下逻辑：

```text
调用 memset 清空 .bss 段
调用 cprintf 输出 "(THU.CST) os is loading ..."
最后进入 while(1) 死循环
```

在当前内核反汇编中也可以看到 `kern_init` 的最后一条循环跳转：

```asm
0x8020003a: j 0x8020003a <kern_init+0x30>
```

这说明内核完成启动信息输出后，停留在死循环中，符合 lab1 最小可执行内核的预期行为。

#### 问题回答

RISC-V 虚拟机加电后，CPU 最初执行的指令位于 `0x1000` 附近。这里是 QEMU 模拟平台的复位入口，属于启动固件代码，而不是我们编写的内核代码。它的作用是完成最早期的启动流程，并将控制权交给 OpenSBI。

OpenSBI 运行在机器态，即 M 模式，负责完成基本硬件初始化，并最终把控制权交给操作系统内核。在本实验的 Makefile 中，QEMU 通过：

```bash
-device loader,file=bin/ucore.img,addr=0x80200000
```

将内核镜像加载到物理地址 `0x80200000`。因此，当 OpenSBI 启动完成后，CPU 会跳转到 `0x80200000`，开始执行内核第一条指令。

`0x80200000` 对应的符号是 `kern_entry`。它首先设置内核栈指针 `sp = bootstacktop`，然后通过跳转进入 `kern_init`。这说明从固件到内核的控制权交接成功，内核开始执行自己的初始化代码。

## 六、实验总结与收获

### 6.1 对操作系统的理解

1. 本实验中的重要知识点及其与 OS 原理的对应关系

| 实验知识点 | 对应 OS 原理知识点 | 含义、关系和差异 |
|------------|--------------------|------------------|
| QEMU 复位地址 `0x1000` | 计算机启动流程 | CPU 加电后不会直接执行操作系统，而是先从硬件指定的复位入口开始执行固件代码。 |
| OpenSBI | Bootloader / 固件 / 特权级 | OpenSBI 类似启动固件，运行在 M 模式，负责初始化并将控制权交给 S 模式内核。 |
| `0x80200000` 内核入口 | 内核加载地址 | 内核必须被加载到链接脚本约定的位置，否则地址相关代码无法正确运行。 |
| 链接脚本 `kernel.ld` | 程序内存布局 | 链接脚本决定 `.text`、`.rodata`、`.data`、`.bss` 等段在内存中的位置。普通应用程序通常由操作系统加载，而本实验内核需要自己精确控制布局。 |
| `la sp, bootstacktop` | 栈和函数调用 | C 函数调用依赖栈保存局部变量、返回地址和寄存器状态。进入 C 代码前必须先准备可用栈。 |
| 清空 `.bss` | C 运行时初始化 | 普通程序由运行时库完成 `.bss` 清零；裸机内核没有外部运行时，需要自己完成。 |
| `ecall` 调用 SBI | 系统调用/特权级切换 | S 模式内核通过 `ecall` 请求 M 模式 OpenSBI 服务。它和用户态通过系统调用进入内核的思想类似，但特权级方向不同。 |
| `cprintf` 输出链路 | 内核调试输出 | 内核无法依赖宿主机标准库，需要自己实现格式化输出，并通过底层固件或设备驱动输出字符。 |

2. OS 原理中重要但本实验没有完整覆盖的知识点

- 中断处理：lab1 尚未建立 trap 向量，也没有处理中断和异常。
- 虚拟内存：lab1 使用简单物理地址启动，尚未建立页表和地址空间抽象。
- 物理内存管理：lab1 没有实现页面分配器，也没有管理空闲物理页。
- 进程和线程：lab1 只有一个内核执行流，没有进程控制块、上下文切换和调度。
- 系统调用完整机制：本实验只使用 S 模式到 M 模式的 `ecall` 调用 OpenSBI，没有实现用户态到内核态的系统调用。
- 文件系统：lab1 没有存储抽象、目录、文件读写等功能。
- 并发与同步：lab1 没有锁、信号量、条件变量等并发控制机制。
- 设备驱动：本实验通过 OpenSBI 简化输出，没有真正实现串口、键盘等设备驱动。

## 七、实验结论

通过本次实验，我们理解并验证了 lab1 最小可执行内核的启动过程。QEMU 模拟的 RISC-V 虚拟机从复位地址 `0x1000` 开始执行固件代码，经由 OpenSBI 完成基础初始化后，将控制权交给加载在 `0x80200000` 的内核入口 `kern_entry`。内核入口首先设置内核栈，然后跳转到 C 语言函数 `kern_init`。`kern_init` 完成 `.bss` 清零，通过 `cprintf` 输出启动信息，最后进入死循环。

本实验虽然代码量不大，但覆盖了操作系统启动中非常关键的基础概念：固件、特权级、内核入口、链接脚本、栈初始化、裸机 C 运行环境和调试方法。这些内容为后续实验中的中断、内存管理、进程管理和系统调用机制打下了基础。
